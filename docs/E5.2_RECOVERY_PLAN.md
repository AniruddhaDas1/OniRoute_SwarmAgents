# E5.2 Recovery Plan Builder

## Phase E5.2 — Recovery Plan Generation

**Version:** v1.2.1
**Status:** Implemented
**Pipeline:** E4.x Review Pipeline → E5.1 Assessment → E5.2 Plan → E5.3 Execution

---

## 1. Overview

E5.2 is the **plan generation** phase of the E5 self-healing and recovery system. It takes the output of E5.1 (RecoveryAssessment) and produces a structured, deterministic RecoveryPlan that E5.3 can execute.

**E5.2 is RESPONSIBLE for:**
- Converting findings to repair actions
- Grouping related findings
- Determining action ordering
- Building dependency graph
- Ensuring determinism

**E5.2 is NOT responsible for:**
- Executing repairs
- Calling providers
- Modifying files
- Performing retries

```

### 2.2 Key Components

#### RecoveryAssessment (E5.1 output)
The output of E5.1, containing:
- Eligibility determination
- Grouped findings
- Severity/category summaries
- Affected artifacts/files

#### RecoveryPlanBuilder (E5.2)
The plan generation engine that:
- Takes RecoveryAssessment as input
- Groups findings by artifact
- Maps categories to action types
- Orders actions deterministically
- Produces RecoveryPlan

#### RecoveryPlan (E5.2 output)
The structured recovery plan containing:
- Ordered repair actions
- Finding traceability
- Dependency information
- Evidence chain

## 3. Finding → Repair Action Mapping

### 3.1 Category to Action Type Mapping

| Finding Category | Repair Action Type | Auto-Repairable |
|-----------------|-------------------|-----------------|
| SYNTAX | FIX_SYNTAX | Yes |
| STRUCTURE | FIX_STRUCTURE | Yes |
| CONFIGURATION | FIX_CONFIGURATION | Yes |
| DEPENDENCY | FIX_DEPENDENCY | Yes |
| PLACEHOLDER | REMOVE_PLACEHOLDER | Yes |
| CONTENT | FIX_CONTENT | Yes |
| FILESYSTEM | MANUAL_REVIEW | No |
| SECURITY | MANUAL_REVIEW | No |
| CONTRACT | MANUAL_REVIEW | No |
| QUALITY | MANUAL_REVIEW | No |
| OTHER | MANUAL_REVIEW | No |

### 3.2 Manual Review Boundary

Security, contract, and quality findings are **never** automatically converted to repair actions. They produce `MANUAL_REVIEW` action types that:

- Cannot be auto-repaired
- Require human intervention
- Are marked with `requires_manual_review: True`
- Are placed at the end of the action queue

## 4. Grouping Rules

### 4.1 Grouping Criteria

Findings are grouped by the combination of:
- **Artifact ID**: The artifact that produced the finding
- **File Path**: The file containing the issue

### 4.2 Grouping Behavior

When multiple findings affect the same artifact+file:

1. They are combined into a single recovery action
2. The primary category is determined by the most common category
3. The max severity is the highest severity among grouped findings
4. All finding IDs are preserved for traceability

### 4.3 Example

```
file.py:
  - syntax error (finding-1)
  - malformed import (finding-2)  
  - dependent reference failure (finding-3)
  
Result: Single action with finding_ids=[finding-1, finding-2, finding-3]
```

---

## 5. Ordering Rules

### 5.1 Deterministic Ordering

Actions are ordered deterministically by a composite key:

1. **Priority** (severity-based): CRITICAL (0) < ERROR (1) < WARNING (2) < INFO (3)
2. **Category order**: SYNTAX < STRUCTURE < CONFIGURATION < DEPENDENCY < ...
3. **Action type order**: FIX_* < MANUAL_REVIEW
4. **Artifact ID**: Alphabetical for tie-breaking

### 5.2 Category Ordering (Foundational First)

1. SYNTAX (0) - Foundational, must work first
2. STRUCTURE (1) - Foundational
3. CONFIGURATION (2) - Foundational
4. DEPENDENCY (3) - Can depend on config
5. PLACEHOLDER (4)
6. CONTENT (5)
7. FILESYSTEM (6)
8. SECURITY (7) - Manual review
9. CONTRACT (8) - Manual review
10. QUALITY (9) - Manual review
11. OTHER (10)

### 5.3 Example

```
Input findings:
  - art-1/file.py: WARNING (placeholder)
  - art-2/file.py: ERROR (syntax)
  - art-3/file.py: CRITICAL (syntax)

Output order:
  1. art-3/file.py: CRITICAL syntax (priority 0)
  2. art-2/file.py: ERROR syntax (priority 1)
  3. art-1/file.py: WARNING placeholder (priority 2)
```

## 6. Dependency Handling

### 6.1 Dependency Categories

Certain finding categories indicate dependencies:
- **DEPENDENCY**: Findings in this category suggest artifact dependencies
- **FILESYSTEM**: May indicate file ordering issues

### 6.2 Foundational Categories

Certain categories are foundational (should be fixed first):
- CONFIGURATION
- STRUCTURE
- SYNTAX

### 6.3 Dependency Resolution

The current implementation orders actions by category priority. Future E5.3 may implement explicit dependency graphs for more complex dependency chains.

Every recovery action preserves traceability to its source:

```

    ↓

    ↓

    ↓
QualityGateResult (E4.2)

### 7.2 Evidence Preservation

The RecoveryPlan includes:
- `assessment_id`: Link to E5.1 assessment
- `readiness_id`: Link to E4.3 result
- `gate_id`: Link to E4.2 result
- `finding_ids`: All finding IDs in each action
- `evidence_refs`: Evidence references from findings
- `evidence` dict: Complete evidence chain

## 8. Determinism

### 8.1 Deterministic Requirements

The same input must always produce:
- Identical actions
- Identical ordering
- Identical classifications
- Identical plan hash

### 8.2 Non-Deterministic Elements Avoided

- Timestamps in hash computation
- Random UUIDs
- Memory addresses
- Unordered collections (use tuples)
- Dictionary iteration order (sort keys)

### 8.3 Plan Hash Computation

```python
def compute_recovery_plan_hash(plan: RecoveryPlan) -> str:
    hash_payload = {
        "plan_id": plan.plan_id,
        "assessment_id": plan.assessment_id,
        "readiness_id": plan.readiness_id,
        "gate_id": plan.gate_id,
        "eligibility": plan.eligibility.value,
        "total_actions": plan.total_actions,
        "total_groups": plan.total_groups,
        "findings_addressed": plan.findings_addressed,
        "action_ids": sorted([a.action_id for a in plan.actions]),
        "action_orders": sorted([a.order for a in plan.actions]),
    }
    json_bytes = json.dumps(hash_payload, sort_keys=True).encode("utf-8")
    return hashlib.sha256(json_bytes).hexdigest()
```

## 11. Usage Example

```python
from runtime.contracts.e5_engine import (
    RecoveryAssessmentEngine,
    RecoveryPlanBuilder,
)

# E5.1: Create assessment
assessment_engine = RecoveryAssessmentEngine()
assessment = assessment_engine.create_assessment(
    readiness_result,  # From E4.3
    gate_result,       # From E4.2
)

# E5.2: Build plan
plan_builder = RecoveryPlanBuilder(max_recovery_attempts=3)
plan = plan_builder.build_plan(assessment)

# Verify plan
print(f"Plan ID: {plan.plan_id}")
print(f"Actions: {plan.total_actions}")
print(f"Hash: {plan.plan_hash}")

# For each action in plan:
for action in plan.actions:
    print(f"  [{action.order}] {action.action_type.value}: {action.description}")
```

## 12. Limitations

### 12.1 Current Limitations

1. **No explicit dependency graph**: Dependencies are handled implicitly through ordering
2. **No action retry tracking**: E5.3 will handle retry logic
3. **No file modification simulation**: E5.3 will simulate actual repairs

### 12.2 Future Enhancements

1. Explicit dependency graph between artifacts
2. Action preconditions and postconditions
3. Dry-run mode for plan validation
4. Plan comparison and diff
