# E5.3 Recovery Engine

Phase E5.3 — Self-Healing and Recovery Execution.

## Overview

The Recovery Engine is the **execution layer** of the E5 self-healing pipeline. It takes a `RecoveryPlan` from E5.2 and performs real file-based repairs on the generated workspace.

## Architecture

```
ReleaseReadinessResult (E4.3)
        ↓
RecoveryAssessmentEngine (E5.1)
        ↓
RecoveryAssessment (E5.1 output)
        ↓
RecoveryPlanBuilder (E5.2)
        ↓
RecoveryPlan (E5.2 output)
        ↓
RecoveryEngine (E5.3)
        ↓
RecoveryResult
        ↓
E4.1 Re-review (loop)
```

## Components

### RecoveryEngine

The main orchestrator that:
1. Creates assessment (E5.1)
2. Builds plan (E5.2)
3. Executes repairs with bounded retries
4. Returns plan and result

### RepairExecutor

Executes individual repair actions:
- **FIX_SYNTAX**: Removes trailing whitespace, fixes common syntax issues
- **FIX_STRUCTURE**: Verifies directory structure exists
- **FIX_CONFIGURATION**: Cleans up config files
- **FIX_DEPENDENCY**: Cleans up dependency files
- **REMOVE_PLACEHOLDER**: Removes TODO/FIXME/PLACEHOLDER markers
- **ADD_FILE**: Creates missing files with default content
- **FIX_CONTENT**: Cleans up content files

## Key Behaviors

### Bounded Retries

- Maximum 3 attempts per action
- Respects action's `max_retries` setting
- No infinite retries
- Terminal failure after max attempts

### Workspace Security

- All file operations stay within workspace root
- Absolute paths are rejected
- Path traversal (`../`) is blocked
- Engine root files are protected

### Evidence Preservation

Every recovery attempt creates a `RecoveryAttempt` record:
- Unique attempt ID
- Action ID
- Attempt number
- Status (SUCCESS, FAILED, BLOCKED, MANUAL_REVIEW_REQUIRED)
- Before/after state
- Timing information
- Result message

### Dependency Awareness

- Actions with unmet dependencies are blocked
- Dependent actions wait for prerequisites
- Independent actions can proceed

## Recovery Status Values

- **RECOVERABLE**: Recovery succeeded
- **NOT_RECOVERABLE**: Requires manual review
- **NOT_NEEDED**: No recovery needed
- **TERMINAL_FAILURE**: Failed after max retries

## Usage

```python
from runtime.contracts.e5_engine import RecoveryEngine

# Initialize engine
engine = RecoveryEngine(
    workspace_root="/path/to/workspace",
    max_recovery_attempts=3
)

# Execute recovery
plan, result = engine.recover(
    readiness_result=release_readiness_result,
    gate_result=quality_gate_result  # optional
)

# Check result
if result.success:
    print("Recovery succeeded!")
    print(f"Modified files: {result.modified_files}")
else:
    print("Recovery failed")
    print(f"Remaining findings: {result.remaining_findings}")
```

## Integration Points

### E4.1 Review Engine

After repairs, the Recovery Engine can trigger re-review through E4.1 to verify fixes.

### InvocationEngine (LLM)

For LLM-based repairs, the engine routes through `InvocationEngine`:
- Does NOT call providers directly
- Does NOT bypass UMAL
- Uses existing generation architecture

## Boundary Conditions

### Manual Review Actions

These action types are NOT auto-repaired:
- `MANUAL_REVIEW`: Requires human intervention
- `REGENERATE`: Requires LLM regeneration through InvocationEngine

### Security/Contract/Quality Findings

These findings produce `MANUAL_REVIEW_REQUIRED` status and are skipped during auto-repair.

## E5.3 vs E5.1/E5.2 Responsibilities

| Phase | Responsibility |
|-------|---------------|
| E5.1 | Assess recovery eligibility |
| E5.2 | Generate recovery plan |
| E5.3 | **Execute repairs** |

E5.2 is PLAN GENERATION ONLY.
E5.3 is EXECUTION ONLY.
